# 飞书通知与网站联调

## 观察提醒聚合（2026-10-29 本地实现）

MA/MACD交叉与支撑观察在同一轮监控结束后按币种合成一条观察消息，保留各周期、
各指标、支撑价和参考价。开仓、平仓、系统故障仍按原路径逐条入队，不等待观察汇总。
聚合不改变交易信号、开平仓条件、成本或风险配置。

- 均线和MACD仍按各自的交叉K线去重；新的交叉事件正常播报。
- 同币同周期的同一支撑持续接近时不重复提醒。沿用离开上侧两倍容差后重新触发的
  防抖距离；更换支撑、离开再接近时重新提醒。报价低于原支撑下侧容差区时发送
  跌破观察，即使本轮已选择更低的新支撑，也先说明旧支撑被跌破。这不是收盘确认。
- 支撑状态及最近交叉编号写入事件日志旁的 `*.observations.json`，重启后继续去重。
  状态损坏时保留原文件、暂停观察提醒，并显示“观察提醒状态”异常；开平仓不受此限制。
- 原始事件仍逐条写入日志。完整轮次另追加 `observation_batch`，包含每币消息及
  原始事件编号，不受网站最近50条展示限制。轮次中断时，已取得的信息会标注“本轮检查未完成”。
  重启恢复时合并检查点与原始日志中尚未成组的尾部事件，沿用原轮次编号。
- 飞书队列按持久化字节游标读取整条批记录，首次升级不补发旧历史；发送失败仍以
  完整分组重试。游标、已见编号和待发消息在同次队列保存中写入。
  日志轮转先读取保留备份中的未读内容；备份已丢失会明确显示历史缺口。

本节只描述本地实现。VPS部署、重启和真实消息展示需要对应的发布与访问证据。

## 原有通知联调

本轮实现测试链路：网站「诊断 → 飞书通知联调」分别向信号、系统、研究渠道发送固定测试消息，并显示飞书接口回执和测试编号。不会写入模拟交易或策略信号记录。

配置在根目录 `.env`：

- `FEISHU_SIGNAL_WEBHOOK_URL`
- `FEISHU_SYSTEM_WEBHOOK_URL`
- `FEISHU_RESEARCH_WEBHOOK_URL`
- `FEISHU_TEST_ENABLED`：默认关闭，本地 `scripts/dev_research.py` 开启。
- `FEISHU_SITE_URL`：可选的 HTTPS 网站地址。未配置时明确提示 localhost 仅本机可用。

所有消息包含「炼气」，与机器人关键词设置匹配。Webhook 不传给前端，也不包含在错误信息中。测试接口只接受 JSON POST，渠道固定，串行执行且间隔至少 3 秒。发送超时 12 秒，不自动重试不确定结果，避免重复通知。状态保存在进程内，重启后清空。

## 自动业务通知（2026-09-07 后续接入）

本地入口已开启 `FEISHU_AUTO_ENABLED=true`。每 5 秒检查与网站相同的模拟交易记录、HTML 报告目录及监控异常状态：新信号和模拟退出发到信号群，异常与恢复发到系统群，新报告与更新发到研究群。首次启动建立历史基线，不补发旧信号和旧报告。

`FEISHU_OUTBOX_FILE` 在本地入口指向 `runtime/local-research/feishu-outbox.json`。队列及已观察记录原子落盘，发送失败指数退避重试（最长间隔 300 秒），每轮最多处理 3 条到期消息；等待重试的消息不阻塞其他渠道。自动通知可能在网络超时后重试，因此不能保证绝对只投递一次，消息包含稳定编号供核对。以上重试策略只适用于自动通知，手动测试不重试。整个进程停止时无法自行报警。

网站诊断页每 10 秒刷新自动任务状态、待发送数量和错误。通知在独立后台任务中发送，不阻塞行情监控。当前仅本机启用，未部署 VPS；手机访问暂不调整。

验证：Python 155 项、前端 6 项测试通过，前端构建通过。新增回归覆盖开仓/退出分流、历史去重、故障恢复、报告更新、重启保留失败队列、重试不阻塞其他渠道。真实生成 `feishu-auto-integration-20260907/report.html` 后，研究群自动收件；在飞书点击链接成功打开同名网站报告。未向真实模拟账本插入测试持仓，真实行情开仓至退出的完整周期仍待自然触发验证。

## 综合复测与顺序修复

2026-09-07 综合测试编号 `composite-1788789285`：隔离夹具生成开仓、报告、故障、退出、恢复共 5 条通知。先注入发送失败，验证队列重载后保留，再恢复投递；3 个真实群均收到带「综合测试」标识的消息。重复观察与重新载入后没有新待发送记录。测试夹具没有写入网站真实模拟账本。

追加测试发现：开仓失败后，后来的退出消息可能越过它。已修复为同一渠道先进先出，失败或等待重试时暂停该渠道，其他渠道仍可处理。回归先复现 `open, closed, report` 的错误次序，再验证 `open, report`，恢复后按 `open, closed` 投递。网站模拟生命周期与通知输入组合回归也验证：开仓在网站可见、退出后移入历史，对应通知各一条。完整 Python 测试 157 项通过，前端 6 项通过；本地服务已加载修复。

顺序保证是本地发送顺序，不保证网络超时后飞书绝不重复收件。若某渠道永久配置错误，该渠道后续消息会排队，网站显示待发送数量；需要修复配置后恢复。

实际报告回链复核进一步发现旧服务被 SSE 长连接拖住退出，同一报告出现两个相同编号的通知。已清理旧进程，增加 `SenderLease` 操作系统文件锁，同一个 outbox 只允许一个服务发送；本地启动器设置 `timeout_graceful_shutdown=5`。锁冲突时新任务显示初始化失败，需要旧实例释放后重启新服务，不会静默并发发送。新增锁占用/释放回归，完整 Python 测试更新为 158 项通过。

## 系统异常的分类与去重

系统消息按实际故障模块分类：行情、策略信号、技术指标、支撑位监控、模拟持仓行情、
模拟币池扫描/更新、模拟交易账本、事件记录、市场摘要和站点巡检。模拟持仓报价不可用
归入“模拟持仓行情”，不再统一显示“信号计算”；品种、周期和安全错误摘要在网站诊断中保留。
空文本的超时也保留异常类型，不能被判为成功。

站点巡检达到既有连续失败阈值后才进入飞书异常通知；单次失败仍在网站显示，但不立即
入队。巡检任务自身连续失败也遵循相同阈值，成功执行后清除该任务的失败计数。

每个故障模块独立持久化告警状态。持续异常只通知一次，新模块加入只通知新增项；组合
增减或排列变化不重发已有故障。每个模块连续恢复至少 60 秒后发送注明模块的恢复消息，
不足 60 秒就复发不重新告警。旧 outbox 的 `fault/recovery_since` 会保留已有告警及恢复等待；
开平仓、报告通知、失败重试和单发送者锁规则不变。

## 模拟持仓行情告警门槛与取证

`paper_data` 首轮失败立即出现在网站诊断，但只有连续至少 3 个完成的监控轮失败、
且持续至少 60 秒才进入飞书系统告警。通知任务每 5 秒查看同一状态不会增加失败轮数。
已告警故障短暂恢复后 60 秒内复发保持原告警；持续恢复至少 60 秒才发恢复通知。
此门槛只控制通知，实时点价仍必须通过原有 30 秒来源时间保护，过期报价不能成交。

故障状态写入账本同目录的 `monitor-faults.json`，安全事件追加到 `monitor-faults.jsonl`；
可用 `MONITOR_FAULT_FILE` 指定独立路径。记录包含首次/最近故障时间、失败轮数、品种、
周期、源报价年龄、请求异常类型、告警升级和恢复。成交时间过旧与请求/K 线失败分别记录，
原始异常文本、URL 和凭据不入历史。状态损坏或写入失败会显式显示“故障记录”异常。

`GET /api/diagnostics/faults` 返回当前与最近故障及最多 50 条安全事件；
`/api/state` 的 `paper_data_fault` 提供当前门槛与诊断状态。发布验收使用隔离故障状态及
outbox 向飞书发送明确标记的测试消息，不向生产模拟账本注入测试交易或故障。

## 自动通知耗时取证（本地实现，待单独发布）

`GET /api/notifications/status` 的 `automatic.delivery_timing` 提供当前待发消息的最老
入队年龄、未知年龄数量、最近最多 20 次尝试，以及持久化保留窗口内的耗时摘要。
窗口最多保留 200 次尝试；`retained_count` 是当前保留数量，不代表全部历史或消息总数。
`accepted_count`、`failed_count`、`inflight_count` 也只统计这个窗口。成功的 `accepted`
仅表示飞书服务业务响应接受消息，不能证明客户端已展示或用户已读。

每条新队列消息记录原始 `created_at` 与实际 `enqueued_at`。指标/支撑事件使用原事件的
`created_at`，模拟开平仓使用 `opened_at`/`closed_at`，报告使用文件版本的 `updated_at`
（文件修改时间），系统异常/恢复通知使用实际产生该通知的时刻。它们不是 K 线收盘时间，
不能把等待 K 线或上游信号计算耗时归为飞书网络耗时。旧队列缺失的原始或入队时间保留
`null`，不以升级、重启或首次重试时间补造。

每次发送前，先将 `attempt_started` 记录及尝试序号原子写入原 outbox，再调用发送函数。
完成后同一记录更新为 `accepted` 或 `failed`，包含以下白名单字段：

| 字段 | 含义 |
| --- | --- |
| `message_id` | 原通知 key 的 SHA-256 前 24 位，用于跨重启、重试关联，不返回原始 key |
| `channel`、`attempt`、`stage` | 渠道、本条消息的尝试序号、本次尝试阶段 |
| `created_at`、`enqueued_at`、`attempt_started_at` | 来源产生、实际入队、开始本次尝试的 Unix 秒时间 |
| `accepted_at`、`failed_at` | 本次尝试完成的 Unix 秒时间；只填写对应结果的一项 |
| `queue_wait_s` | 从入队到本次尝试开始的秒数；重试时包括此前等待及尝试耗时 |
| `send_duration_s` | 本次发送调用耗时，使用单调时钟，不受系统时间校准影响 |
| `total_age_s` | 来源产生到本次尝试完成的秒数 |
| `retry_delay_s` | 本次失败后安排的退避秒数；成功为 0，未结束为 `null` |
| `error_class`、`clock_skew` | 安全错误类别、是否检测到墙上时钟倒退或时间次序异常 |

历史和摘要不保存标题、正文、webhook、URL、原始异常文本或完整发送返回值。消息正文仍
按原有设计只留在待发送队列中供实际投递。`last_delivery` 同时返回匿名关联与耗时字段，
失败信息只显示安全类别。`channels.*.sent_at` 保留原兼容含义（调用开始时间），增加的
`attempt_started_at`、`accepted_at`/`failed_at`、`send_duration_s` 明确区分开始和完成。

若进程在网络调用期间中断，保留 `attempt_started`，归入 `inflight_count`，表示结果仍在
进行或已无法确定；不能推断成功或失败。重启继续保留原 FIFO 和到期重试规则，并使用下一个
尝试序号。网络超时或中断后重试依然可能重复投递，不承诺恰好一次。单发送者锁、每轮最多
3 条、同渠道顺序、失败退避和独立故障恢复门槛保持不变。

摘要中的 `queue_wait_s`、`send_duration_s`、`total_age_s` 各返回有效样本的 `count`、
最近秩定义的 `p50`/`p95` 和 `max`，单位均为秒；不包含未结束尝试或未知数据，空窗口的
分位数与最大值为 `null`。发现时钟倒退时，相应墙上时钟年龄返回 `null` 并标记
`clock_skew=true`，不会伪装成 0。`pending_oldest_age_s` 以入队时间计算；只要有待发消息
缺少有效入队年龄就返回 `null`，并由 `pending_unknown_age_count` 明示缺口。

## 排队调度优化

生产入口每 0.5 秒观察新事件；到期积压按下一次发送时间继续调度。
自动队列仍每次最多尝试 3 条，但不再把“一批完成”视为必须等待 5 秒的理由。
`Outbox.next_due_delay(allowed_channels)` 仅检查各启用渠道的首条待发消息，返回最早
到期等待秒数：`0` 表示可以续批，正数表示仍有重试或限速等待，`None` 表示当前没有
启用渠道的待发任务。禁用渠道以及被失败队头挡住的后续消息不能触发空转或越过队头。
失败渠道进入原有退避时，其他渠道仍可在全局限速允许后独立发送。

[飞书自定义机器人官方说明](https://open.feishu.cn/document/client-docs/bot-v3/add-custom-bot)
规定单个机器人每分钟最多 100 次请求、每秒最多 5 次请求。生产调用显式设置
`Outbox(path, min_send_interval_s=0.7)`，三个渠道共用最小发送开始间隔，约每分钟
86 次，兼容多个渠道配置同一个机器人的情况。默认值为 `0.0`，仅用于兼容旧调用及离线
测试；生产入口不依赖这个默认值。失败、超时、结果未知的发送也占用本次间隔。

`send_pacing` 的 `last_attempt_at`、`not_before`、`interval_s` 随发送前的
`attempt_started` 一起原子落盘。等待限速不会增加尝试序号或生成假尝试。进程内用单调
时钟保留限速期限；预发送落盘完成后，按真实发送调用起点重新预约完整间隔，慢 fsync
不能消耗请求之间的限速额度。完成记录保存真实 `attempt_started_at`：预发送落盘耗时
计入 `queue_wait_s`，不计入 `send_duration_s`。未结束记录中的预落盘起点只是预约时刻，
不能作为真实网络调用起点。重启通常按持久时间恢复剩余间隔；若最近尝试仍是未知的
`attempt_started`，保守等待完整一个间隔。若重启后发现墙上时钟倒退，也最多保守
等待完整一个已存/当前较大间隔，避免忽略限速或被一个未来绝对时间卡住数小时。
原有业务失败的 `next_attempt` 及指数退避策略保持不变。

`deliver(..., should_stop=...)` 在开始下一次尝试前检查停止信号，返回本轮
`attempted`、`accepted`、`failed`、`stopped`、`next_due_delay_s`。不新增并发发送者，
仍按原队列位置遍历、同渠道 FIFO；已开始的请求不因停止信号被假定取消或接受。
状态摘要 `automatic.delivery_timing` 同时提供 `min_send_interval_s`、
`pacing_delay_s`、`next_due_delay_s`；后台传入实际启用渠道，避免把暂停渠道当成就绪。

较短的观察间隔不再导致相同 outbox 反复写盘：`save()` 比较最后一次成功原子替换的
不可变 JSON 内容，无变化且目标文件仍存在时跳过临时文件、fsync 和替换。新队列、
格式升级、嵌套内容变化和文件被删除后重建仍会落盘；写入、fsync 或替换失败不会更新
缓存，后续保存会继续重试。匿名计时历史、去重记录、故障模块及恢复门槛保持原含义。
